.. js:method:: ContreeClient.iterOperationEvents(operationId, options?)

   ``GET /operations/{operationId}/events`` — Stream the operation event log via Server-Sent Events

   Always returns ``text/event-stream`` (SSE) on success.  The body
   is a sequence of three kinds of lines (per RFC W3C SSE), each
   terminated by ``\n\n``:

   .. rubric:: Frame shapes


   **Normal event frame** — one ``OperationEvent`` JSON object in
   ``data:``, dispatchable via ``event:``:

   ::

       id: <integer event.id>
       event: <OperationEventType, e.g. stdout|stderr|spawn|exit>
       data: {"id": N, "ts": "...", "spid": ..., "type": "...", "data": {...}}

   ``event:`` always matches ``data.type``.  See ``OperationEvent`` and
   ``OperationEventType`` for the per-type payload shape.  Native
   ``EventSource`` dispatches each frame to the matching
   ``addEventListener("<type>", ...)`` handler.

   **Server-side error frame** — surfaces handler exceptions to
   the connected client without tearing the TCP connection down
   mid-stream.  Sent right before the server closes the response:

   ::

       : stream ended with error, retry since last event id

       event: sse_error
       data: <one-line exception message>

   The leading SSE comment line lets pure-EventSource clients see
   the intent ("retry from Last-Event-Id"); the ``sse_error`` frame
   carries the error text for logging.  Clients should treat this
   as a non-clean close and reconnect with the standard SSE
   ``Last-Event-Id`` semantics (see Resuming).

   **Keepalive comment** — periodic ``: keepalive\n\n`` lines
   emitted while the stream is idle.  They keep upstream
   ``proxy_read_timeout`` / TCP idle timers fresh and have no
   application meaning.  Spec-compliant; EventSource and any SSE
   parser must ignore comment lines (those beginning with ``:``).

   .. rubric:: ``follow`` semantics


   The ``follow`` parameter controls only whether the stream stays
   open after the last currently-known event:

     * ``follow=0`` (default) — the server emits everything
       currently available and closes the connection.

     * ``follow=1`` — same start; if the operation is still
       running the server keeps the connection open and forwards
       new events as they appear.  For terminal operations
       ``follow=1`` is a no-op: there's nothing more to subscribe
       to, so the connection closes after the last event just
       like ``follow=0``.

   Optional filters:

     * ``?spid=N`` — only events whose ``spid`` (Spawned Process ID,
       the routing identity in ``OperationEvent``) matches.

     * ``?since=N`` — only events with ``id > N``.

   ``follow=1`` requires ``SPAWN`` or ``SPAWN_DISPOSABLE`` on top of
   the baseline ``LIST`` — a long-lived subscription reserves
   per-operation server state.  ``follow=0`` is read-only and
   stays under ``LIST``.

   .. rubric:: Resuming after a drop


   Every normal frame carries ``id:`` — the canonical event id.
   On reconnect send the last successfully received id in the
   standard ``Last-Event-Id`` request header (or ``?since=N`` on
   manual GETs); the server resumes from that point.

   .. rubric:: Error handling


   .. list-table::
      :header-rows: 1

      * - Status
        - Meaning
        - Client action
      * - 200
        - Stream open
        - Read frames; reconnect with Last-Event-Id if the stream closes
          before reaching a terminal event
      * - 400
        - Malformed query/header (non-integer param)
        - Fix request
      * - 401
        - Missing/invalid auth
        - Refresh credentials
      * - 403
        - Auth lacks LIST (or SPAWN for ``follow=1``)
        - Use a token with the right scope
      * - 404
        - Operation not in this namespace
        - Wrong UUID
      * - 410
        - Stream is over but the terminal artifact isn't ready yet
        - Retry after ``Retry-After``
      * - 425
        - Not yet ready (operation is still being prepared)
        - Retry after ``Retry-After``
      * - 502
        - Upstream returned an error opening the stream
        - Retry; if persistent, escalate
      * - 504
        - Upstream took too long to respond
        - Retry


   A ``200`` followed by an ``event: sse_error`` frame and immediate
   close is the in-band equivalent of "the stream broke after we
   already committed to a 200" — handle it the same way as 410:
   wait briefly, reconnect with ``Last-Event-Id``.

   See ``OperationEvent`` for the per-event shape.

   :param operationId: ``string`` — The ID of the operation Example:
      ``12345678-9abc-baba-deda-0123456789ab``.
   :param options.follow: ``boolean`` — HTTP-flag boolean. Present without
      a value (``?follow``) and ``?follow=1`` both enable; ``?follow=0``
      and absence disable. When enabled, the SSE stream stays open after
      the currently-known events have been sent — for a running operation
      new events are forwarded as they appear; for a terminal operation it
      has no effect.
   :param options.spid: ``number | null`` — Only emit events whose ``spid``
      field matches. Filter is applied server-side regardless of whether

   :param options.since: ``number | null`` — Only emit events with

.. js:method:: ContreeClient.operationSubprocessStdin(operationId, spid, value, options?)

   ``POST /operations/{operationId}/subprocesses/{spid}/stdin`` — Write to a subprocess's stdin and/or close it

   Writes a chunk to the stdin of a live process inside the
   running instance — ``spid=1`` targets the main process, ``≥2`` the
   exec'd children.  Requires the process to have been started
   with ``stdin.close=false``; otherwise its pipe is already at EOF
   and the call returns 409.

   ``close=true`` (the default) signals EOF after writing ``value``;
   an empty ``value`` with ``close=true`` just closes the pipe.  A
   client that serializes its own requests gets ordered writes;
   concurrent requests to the same spid are safe but their order
   is unspecified.

   A 504 means the guest write timed out mid-call — the chunk may
   or may not have been delivered (e.g. the process stopped
   reading and the pipe is full), so blind retries can duplicate
   data.

   :param operationId: ``string`` — The ID of the operation Example:
      ``12345678-9abc-baba-deda-0123456789ab``.
   :param spid: ``number`` — Spawn id (1 = main process; ≥2 = exec'd
      children).
   :param value: ``string`` — Content to write to stdin (may be empty for a
      close-only request) Example: ``aGVsbG8K``.
   :param options.encoding: ``"ascii" | "base64" | undefined`` — Encoding
      of the content
   :param options.close: ``boolean | undefined`` — ``true`` (default)
      closes stdin (EOF) after writing ``value`` — the pre-existing
      one-shot behavior. ``false`` keeps the pipe open so more data can be
      sent later via
      ``POST /operations/{operationId}/subprocesses/{spid}/stdin``.
   :returns: ``Promise<null>``

.. js:method:: ContreeClient.applyInstanceFile(operationUuid, fileUuid, path, options?)

   ``POST /operations/{operation_uuid}/files`` — Apply an uploaded file to a running instance

   Reads a file previously uploaded through POST /files and writes it to a
   running INSTANCE operation, including disposable instances. Requires
   LIST
   and the permission used to start the instance. Both the operation and
   the
   uploaded file must belong to the request namespace. Expired files are
   unavailable.
   The assigned worker streams the stored object to the guest through RPC.
   Init records request metadata in ``inspect`` events and the terminal
   publication result in ``file_upload``, including ``fileUuid`` and byte
   count.
   File contents do not enter operation events.

   With unpack omitted or false, path is the full destination filename.
   Missing parent directories are created. The file is published atomically
   after
   transfer and SHA256 verification. The new file has mode 0644 and is
   owned by the guest runtime user. With replace true, an existing leaf
   symlink is replaced.
   Directories and special files are not regular file destinations.

   With unpack true, path is the destination directory. Supports tar,
   tar.gz and tar.bz2; compression is detected from the stored bytes. Xz is
   unsupported and rejected before subsequent chunks are sent. Without
   unpack,
   compressed archives are copied unchanged. Content-Type describes this
   JSON
   request and never controls extraction.

   Extraction accepts regular files, directories, symlinks and hardlinks to
   regular files already extracted in the staging tree. Parent symlinks
   inside that tree are
   not followed. Absolute entry names and entries containing '..' are
   rejected.
   procfs, sysfs, devices, FIFOs and sockets are unsupported. New
   directories
   have mode 0755; regular files retain tar permission bits (0777).
   Ownership
   and timestamps are not restored. Other entries fail explicitly.
   With replace omitted or false, any existing destination returns 409,
   including
   a symlink or empty directory. This condition is checked again atomically
   at publication.
   replace true permits an existing destination. With merge omitted or
   false,
   directory replacement removes the entire old tree without merging
   contents.

   Archives are extracted into a temporary sibling directory. The
   destination
   remains unchanged until the complete stream and SHA256 have been
   verified.
   Without merge, publication uses an atomic rename or exchange, then
   removes the old tree.
   Root and mount-point replacement are unavailable. Existing open
   descriptors
   can still refer to old inodes; concurrent workload access is not a
   snapshot.

   merge true requires both unpack true and replace true. After complete
   staging
   and verification, it combines directories and atomically replaces
   individual
   files and symlinks. Existing entries absent from the archive remain.
   Destination
   directory symlinks are not followed; directory/file conflicts fail
   explicitly.
   Same-filesystem hardlinks are retained. Crossing a destination mount
   requires
   copying file bytes and does not preserve hardlinks across filesystems.
   Merge is not atomic for the whole tree: errors, cancellation or timeout
   after
   application starts can leave completed changes. These changes are not
   rolled back.

   Returns 204 only after completion. Transfers have a 300-second deadline
   and bounded buffers and handles. Disconnect or VM exit cancels the
   transfer.
   A lost response can leave an uncertain outcome; requests are not
   replayed
   automatically. This endpoint does not write to a completed result image.

   A transfer timeout does not stop the instance. Before publication or
   merge starts, cancellation
   preserves the old destination and removes the temporary file or
   extraction tree.
   A timeout while awaiting the final response can occur after publication;
   it does not prove that no changes were made. An old-tree cleanup failure
   is
   reported as an error after publication; it does not roll back the new
   tree.
   The uploaded source object retains its normal lifetime. Automatically
   created
   parent directories have mode 0755 and can remain after errors.

   The primary command's timeout follows normal instance finalization:
   ordinary
   instances persist their filesystem, including successfully published
   uploads;
   disposable instances do not. Instance shutdown waits for pending upload
   cleanup.
   A timeout or crash of the execution environment can bypass this cleanup
   and does not produce
   a successfully persisted result image through normal finalization.

   :param operationUuid: ``string`` — Example:
      ``12345678-9abc-baba-deda-0123456789ab``.
   :param fileUuid: ``string``
   :param path: ``string`` — Absolute guest filename, or directory when
      unpack is true. Missing parents are created.
   :param options.unpack: ``boolean | undefined`` — Extract tar, tar.gz or
      tar.bz2 instead of copying the stored bytes.
   :param options.replace: ``boolean | undefined`` — Permit an existing
      destination. Without merge, directories are replaced in full.
   :param options.merge: ``boolean | undefined`` — Merge verified archive
      contents. Requires unpack and replace. Can leave partial changes.
   :returns: ``Promise<null>``

.. js:method:: ContreeClient.inspectInstanceGrep(operationUuid, pattern, options?)

   ``GET /operations/{operation_uuid}/inspect/grep`` — Search file contents in running instance

   Regex content search inside the running instance's root filesystem,
   through guest RPC.
   A Go converter translates supported Rust regex syntax to Go regexp.

   Symlinks are never followed during traversal, hidden files are searched,
   ``.ignore`` and ``.gitignore`` rules within each search root are
   respected.
   A NUL byte in the first 64 KiB causes a file to be skipped; a later NUL
   ends that file's search. Go regexp uses linear-time matching.
   The classes \w/\W, \d/\D, and \s/\S use Unicode semantics.
   Unicode properties and case folding are pinned to Unicode 16.0.0,
   matching the image engine.
   Scoped flags, nested class set operations, and bounded expansion of
   large repetitions are supported.
   Expanded patterns share a 1 MiB limit per request. Unsupported syntax
   returns 400 with a pattern
   index and byte offset. Unicode \b/\B, CRLF mode, non-ASCII byte mode,
   and \Q…\E are rejected.
   Use (?-u:\b) for an ASCII word boundary. Smart case examines parsed
   literals.

   Results are a flat, file-ordered list of lines. ``before``/``after``
   request extra
   ``type: context`` lines around each ``type: match`` line, mirroring
   ripgrep's
   --json message type field.

   ``path`` may be repeated to search multiple roots in one call, the same
   way
   ``pattern``/``glob`` already can; results are concatenated in the given
   order
   and share the ``maxTotal`` budget across all of them.
   Results never enter operation events. Reads are live and do not form a
   snapshot.
   procfs, sysfs, devices, sockets, and FIFOs are not searched.
   Requires LIST and the permission used to start this instance.
   Searches have a 10-second budget per root and permit two concurrent
   searches per instance. Reaching the time, depth, or result limit sets
   ``truncated``. Context lines count towards ``maxTotal``. Display text is
   limited to 4096 bytes per line; matching can continue beyond this
   window.

   :param operationUuid: ``string`` — The UUID of the running instance to
      inspect Example: ``12345678-9abc-baba-deda-0123456789ab``.
   :param pattern: ``string | readonly string[]`` — Regex pattern to search
      for. May be repeated (max 16); patterns are OR-ed. Max 1024
      characters each. Example: ``^PermitRootLogin``.
   :param options.path: ``string | readonly string[] | null`` — File or
      directory to search inside the running instance. May be repeated (max
      16) to search multiple roots; results are concatenated in the given
      order, sharing maxTotal across all paths. Defaults to the rootfs
      root. Example: ``/etc``.
   :param options.glob: ``string | readonly string[] | null`` — Glob to
      filter files (ripgrep -g semantics, "!" negates). May be repeated.
      Example: ``*.conf``.
   :param options.maxCount: ``number | null`` — Maximum matches per file
      (hard cap 10000).
   :param options.maxTotal: ``number | null`` — Maximum total matches
      across all files (default 1000, hard cap 10000).
   :param options.case: ``"sensitive" | "insensitive" | "smart" | null`` —
      Case sensitivity mode.
   :param options.before: ``number | null`` — Lines of context to include
      before each match (ripgrep -B semantics, hard cap 50). For symmetric
      context (grep -C n), pass both before and after yourself.
   :param options.after: ``number | null`` — Lines of context to include
      after each match (ripgrep -A semantics, hard cap 50).
   :returns: ``Promise<GrepResult>``

Statuses and events
-------------------

Operation statuses are wire strings: ``PENDING``, ``ASSIGNED``, ``EXECUTING``, ``SUCCESS``, ``FAILED``, ``CANCELLED``. Terminal: ``SUCCESS``, ``FAILED``, ``CANCELLED`` — membership via ``TERMINAL_STATUSES`` / ``ACTIVE_STATUSES`` sets or ``isTerminalStatus(status)``.

Event types: ``init``, ``spawn``, ``stdin``, ``stdout``, ``stderr``, ``exit``, ``truncated``, ``size_cap``, ``network``, ``shutdown``, ``inspect``, ``file_upload``, ``completion``; each maps to its ``EventData*`` payload class below, unknown payloads stay plain objects (``parseEventData``).

.. js:class:: InstanceResourcesLimits(fields?)

   Launch-time limits. CPU sets the VM's vCPU count. memoryMib limits
   each process's address space (RLIMIT_AS, soft and hard) and the
   whole process tree's memory (cgroup memory.max). A request for
   1 MiB is valid and enforces that limit on the workload. The backend
   independently selects a minimum VM RAM allocation for guest boot,
   networking and runtime services, for example 128 or 256 MiB.
   This minimum is an implementation detail and can change. It does
   not increase the requested workload limit.
   A small address-space limit can prevent the executable or runtime
   from loading. It includes stacks, libraries and reserved mappings;
   allocations can fail with ENOMEM even with overcommit enabled.
   Guest kernel and runtime consume part of VM RAM.
   Limits are maxima, not reservations.
   Guest root retains permission to modify cgroups.

   .. js:attribute:: InstanceResourcesLimits.cpu

      ``number`` (optional) — Number of guest vCPUs.

   .. js:attribute:: InstanceResourcesLimits.memoryMib

      ``number`` (optional) — Per-process address-space and process-tree
      memory limit in MiB (1048576 bytes).

   .. js:attribute:: InstanceResourcesLimits.maxLayerBytes

      ``number`` (optional) — Maximum writable layer size in bytes.
      Example: ``1073741824``.

.. js:class:: ProcessResourcesLimits(fields?)

   Launch-time limits for a subprocess and its descendants. Each omitted
   or null field inherits the requested operation limit, not the VM's
   minimum boot memory. CPU/RAM cannot exceed the parent operation.
   Limits are maxima, not reservations. Concurrent processes share VM
   resources and can exhaust the aggregate budget. memoryMib sets
   RLIMIT_AS (soft and hard) before exec and memory.max for the tree.
   RLIMIT_AS includes reserved mappings, stacks and libraries; allocation
   or executable loading can fail with ENOMEM. Descendants inherit it.
   A local cgroup OOM
   kills this process tree. A VM-wide OOM can affect other processes.
   Guest root retains permission to modify cgroups.

   .. js:attribute:: ProcessResourcesLimits.cpu

      ``number | null`` (optional) — Number of guest vCPUs available to the
      process tree. The runtime selects CPU affinity; CPU sets can overlap
      between subprocesses.

   .. js:attribute:: ProcessResourcesLimits.memoryMib

      ``number | null`` (optional) — Per-process RLIMIT_AS and tree
      memory.max in MiB. Swap is disabled for this group.

.. js:class:: OperationEvent(fields?)

   One event in the operation's event log.

   **Process events** carry a Spawned Process ID (``spid``) as
   their routing identity: ``spid=0`` is the daemon (init /
   network / shutdown / size_cap, plus any synthetic stderr
   emitted before a child existed), ``spid=1`` is the main
   process from ``InstanceMetadata``, and ``spid>=2`` are exec'd
   children (Phase 3+).  Spids are Registry-assigned,
   monotonic, and never recycled within an operation; the
   kernel PID (when needed for debugging) lives inside the
   per-type ``data`` payload.

   **System events** (``completion``) describe the operation as
   a whole, not a specific child process — they omit ``spid``
   entirely.

   .. js:attribute:: OperationEvent.id

      ``number`` (required) — Sequential id assigned at append time.
      Strictly increasing within a single operation's event log; gaps are
      possible (rare, after a transient producer-side serialization
      failure). Use this with ``Last-Event-Id`` / ``?since=`` to resume a
      dropped SSE stream. Example: ``42``.

   .. js:attribute:: OperationEvent.ts

      ``Date`` (required) — UTC wall-clock time when the event was emitted.
      Example: ``2026-06-08T20:00:00.123456789Z``.

   .. js:attribute:: OperationEvent.type

      ``OperationEventType`` (required)

   .. js:attribute:: OperationEvent.data

      ``EventData | Record<string, unknown>`` (required) — Per-type
      payload. Clients should switch on ``type`` and validate ``data``
      against the corresponding schema below.

   .. js:attribute:: OperationEvent.spid

      ``number`` (optional) — Spawned Process ID — present on
      process-scoped events (``init``, ``spawn``, ``stdin``, ``stdout``,
      ``stderr``, ``exit``, ``truncated``, ``size_cap``, ``network``,
      ``shutdown``, ``inspect``, ``file_upload``). Absent on
      operation-scoped system events (``completion``), which don't tie to a
      specific child. Example: ``1``.

.. js:class:: EventDataInspect(fields?)

   Metadata for a guest inspect RPC. Init emits a started/completed pair
   with the same requestId. Event IDs order the starts independently of
   completion order. A returned handle links subsequent reads, writes,
   finish, close, and file_upload events. All events use spid=0.

   A successful open/upload only allocates a handle; it does not complete
   the transfer. Read events report RPC bytes, not HTTP client receipt.
